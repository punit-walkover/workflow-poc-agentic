Let the agent run the workflow

How to drop our own runner loop and have a GTWY agent execute canvas workflows when a ticket is created, without losing the things the runner guarantees today: the right step order, approvals, waits that last days, safe tool calls and a clear audit trail.

Short answer

Yes, the agent can drive the workflow, but it should not be the place the workflow state lives. The pattern every serious support product converged on (Decagon AOPs, Intercom Fin Procedures, Sierra, Rasa CALM, Parlant) is: the agent drives, our server guards.

The GTWY agent talks to the customer, decides what to do, and calls tools. Our server holds the ticket's current step, variables, loop counts and pending approvals, and every tool call is checked against that state. The step-by-step runner loop (decide → act → advance → flush → wait) goes away; what stays on our side is a small event inbox, a set of workflow tools, and a timer sweeper.

Letting the model hold everything in its prompt and memory is not robust enough today: GTWY keeps about 3 turns of history without tool results, has no durable waits or approval pause, and benchmark data shows tool-calling agents follow written policies inconsistently (τ-bench: under 50% task success, about 25% pass^8 in retail).

Could Mastra or Agno do this for us?

Both are agent frameworks that could replace GTWY as the place the agent loop runs. Neither can run our canvas directly: their workflows are code-composed (sequence, branch, parallel, loop), with no documented "jump back to any earlier step", so in every option the agent still drives the run through our workflow tools and step engine (option B). The question is only which runtime hosts the agent.

  • Still ours in every option: the step engine and workflow tools (step order, input checks, rules, loop limits, idempotent tool calls), the per-ticket event inbox, and the timer sweeper for reminders and expiry. Agno's scheduler is cron-only, and Mastra's sleep durability is unclear, so neither replaces per-ticket timers.
  • What a framework would save: conversation memory, the approval pause and a monitoring UI. With GTWY we build the approval pause ourselves (a tool that records a pending task) and pass context per turn.

Recommendation. Mastra is the chosen direction: same language as our server, tool approval, and memory in our Postgres. Agno is not pursued (it would add a Python service). A GTWY agent stays as the fallback if Mastra can't be used, for example if no model provider can be agreed; ideally Mastra still calls models through GTWY via an OpenAI-compatible endpoint (Stage 0).

Chosen path: option 3, Mastra, built in the stages below. Option 1 keeps running as the baseline until Mastra passes its spike on the same workflow, tools and test chats (pass^5, latency, cost per ticket). Option 2, a GTWY agent, stays only as the fallback if Mastra can't be used; option 4 is not pursued.

Decided: multi-agent on Mastra, built in stages. We start with one Mastra agent on top of our step engine and wf_* tools (Stages 1–2). Once that passes the spike, we split it into a supervisor/router agent plus one agent per workflow or domain (Stage 3), all sharing the same tools and ticket memory. The server still owns all workflow state, and timers stay on our side.

Roadmap: multi-agent on Mastra

Stage 0

Decide

  • Ask the GTWY team for an OpenAI-compatible endpoint, so Mastra can still call models through GTWY. Otherwise agree which model provider Mastra calls.
  • State lives in our Postgres: Mastra storage for memory and threads, our own tables for workflow runs.
Stage 1

Foundation (no behaviour change)

  • Extract the step engine: move next-step, input, condition, loop-limit, bubble and approval rules from steps.ts into a pure engine.ts (no DB, DBOS or AI). The current runner calls it; unit tests plus one real chat prove nothing changed.
  • Add Mastra to the server with Postgres storage and a configurable model provider. Not connected to customers yet.
  • Build the wf_* tools as Mastra tools over the engine: wf_save_input, wf_choose_case, wf_complete_step, wf_handoff, wf_switch_workflow, call_action. Each returns the next step; approvals and idempotency are enforced; testable through a dev endpoint.
Stage 2

One Mastra agent (spike)

  • A single workflow agent drives "To know Order Status" through the wf_* tools, with memory per ticket and requireApproval tied to our approval tasks.
  • About 20 scripted chats × 5 runs. Exit: ≥ 95% pass^5, no out-of-step tool calls, under ~6 s per reply, known cost per ticket.
Stage 3

Multi-agent

  • A supervisor agent replaces route() and the topic check, and hands each turn to a workflow or domain agent with its own prompt and tools.
  • All agents share the ticket's memory and the same step engine; a shared style guide keeps one voice.
  • Our per-ticket event queue and timer sweeper stay, for reminders, expiry and resume windows.
Watch-outs. A supervisor means two AI calls per message, so more latency and cost. Mastra's APIs change often: pin versions, and remember durable agents are beta.

  • Event inbox: every trigger for a ticket (customer message, approval decided, timer due, team note) is a row. One worker takes the oldest event per ticket, so a ticket never has two agent calls in flight. This replaces the runner loop; it is a queue, not a state machine.
  • Dispatcher: turns one event into one GTWY call. It renders the current step card and progress into variables, adds the tools allowed in this step as extra_tools, and sets thread_id = ticket, sub_thread_id = turn (each turn starts clean; we supply context ourselves).
  • Workflow tools API: the only way the agent can change ticket state. It reuses today's step engine (flow.ts, blocks.ts, loop limits) as a library.
  • Action proxy: business tools (viaSocket flows) are called through our server, never directly by GTWY, so approval rules, idempotency and audit stay in one place.
  • Timer sweeper: one cron job that finds due timers (reminder, expiry, approval timeout) and drops a "timer due" event in the inbox.

How each canvas block runs

The canvas stays exactly as it is. At publish time each block is compiled into a step card: a small JSON the dispatcher can show the agent and the server can validate against. The rule of thumb (Decagon, Fin, Ada): the LLM handles language and judgement; code handles anything with a right answer.

The agent contract

One agent, stable prompt

A single GTWY agent "Ticket0 Workflow Agent". Its system prompt never changes per workflow; the workflow arrives as data in variables. That keeps one prompt to test and version.

You are Ticket0's support agent. You follow the CURRENT STEP below; you never invent steps.
- To finish a step, call the matching wf_ tool. The server decides the next step; read it from the tool result.
- If the customer asks something off-topic, answer briefly, then return to the current step.
- If the customer wants something a different workflow covers, call wf_switch_workflow.
- Never promise an outcome a tool has not confirmed. If a tool returns an error, follow its instruction.

Workflow: {{workflow_name}} (v{{workflow_version}})
Progress: {{progress}}                       ← done steps, collected values (short)
CURRENT STEP: {{step_card}}                  ← type, instruction, what to collect, allowed tools
Customer: {{customer}}   Known values: {{variables}}
Conversation (latest {{n}} messages): {{transcript}}

  • Ticket id is never a model argument. It is injected through variables_path, so a confused model cannot touch another ticket.
  • State in tool results. Every successful tool returns the next step card plus a one-line progress note, so the agent always works from server truth (Anthropic's "ground truth from the environment").
  • Errors teach. A rejected call names the step that is still required and what to do, instead of a bare failure.
  • Few tools per turn. The 8 workflow tools plus at most the current step's business tools; well under the ~20 OpenAI recommends.

Multiple steps can complete in one turn, as long as each is confirmed by a tool. That is how the agent avoids asking for things the customer already said, without skipping anything the server requires.

Waits, timers and approvals without a runner loop

  • Waiting for the customer is just state: waiting_for = customer, plus timer rows for the reminder and expiry. Nothing runs while waiting. The next customer message is a new event.
  • Reminders and expiry are fired by the sweeper. A reminder is a fixed message sent by the server (no LLM needed); expiry closes the run, or parks it if we build the resume window.
  • Approvals: the tool records a pending task and the turn ends. When the team decides, an approval_decided event enters the inbox; the dispatcher calls the agent with "Team approved: …", and the server has already run the approved action before that call, so the agent only reports it.
  • Long gaps (hours or days) cost nothing: state is in Postgres, not in a sleeping process. This is simpler than today's DBOS recv for very long waits.
The one durable piece we still need: the inbox worker and the sweeper must not lose events across restarts. A Postgres table with FOR UPDATE SKIP LOCKED is enough; DBOS queues or Render cron also work. This is far smaller than the current runner.

Reliability rules

  1. One agent call per ticket at a time (inbox lock). Keeps order and stays under GTWY's 20/min per thread.
  2. Every side effect is idempotent: key ticket:step:visit. GTWY can re-run tools (reviewer re-runs, retries, our own retries), so the proxy returns the stored result on repeats.
  3. Webhook replies deduped by message_id; a turn with no reply after N seconds is retried once, then escalated.
  4. Iteration budget 8; if GTWY reports maximum_iteration_limit_reached, the server checks whether the step advanced and, if not, retries with a "you ran out of steps, finish the current step" note.
  5. Hard limits: per run max turns, max tool errors, max same-step repeats → forced handoff with summary.
  6. Version pinning: a ticket's run uses the workflow version it started on, as today.
  7. GTWY outage: events stay in the inbox; after a short retry budget the ticket is escalated with "AI unavailable".
  8. Secrets: workflow tools require a header secret passed in extra_tools[].headers; GTWY adds no auth of its own.

Quality and evals

  • Simulation suite per workflow: opening message, a scripted customer persona, mocked tool responses, success criteria. Run before every publish.
  • Measure pass^k, not one lucky run: run each case 5–8 times; publish only if all pass (Sierra's τ-bench lesson).
  • Automatic checks from our event log: steps skipped, tools called outside their step, inputs rejected, loops hit, handoff rate, turns per ticket, cost per ticket.
  • Side-by-side period: the same workflow can run on the old runner or the agent (per-workflow switch), so we compare outcomes on real traffic before switching over.

Rollout plan

Week 1

Spike: prove adherence

  • Mastra agent (GTWY agent as the fallback) + 4 tools (wf_save_input, wf_complete_step, wf_choose_case, one proxied tool) on "To know Order Status". See the Mastra roadmap for the staged version.
  • 20 scripted conversations × 5 runs. Exit: ≥ 95% pass^5, zero tools called out of step, median turn latency under 6 s.
Week 2

Core engine

  • Step-card compiler, full tool set, dispatcher, inbox with per-ticket lock, webhook reply handler, idempotent proxy.
  • Per-workflow engine switch; timeline fed by tool events.
Week 3

Waits and people

  • Timer sweeper (reminder, expiry, approval timeout), approval events, handoff, workflow switch.
  • Limits and forced handoff; GTWY outage path.
Week 4

Quality gate and migration

  • Simulation runner with pass^k gate on publish; metrics dashboard (adherence, handoffs, cost per ticket).
  • Move workflows one by one; remove the runner once all are migrated and stable for two weeks.

Estimate for one engineer: about 4 weeks to production-ready, with the go/no-go decision at the end of week 1.

Decisions needed

  1. Go with option B (agent drives, server guards) rather than a prompt-only agent?
  2. Model provider for Mastra: GTWY through an OpenAI-compatible endpoint, or a direct provider (Stage 0 of the Mastra roadmap)? Mastra is the chosen runtime; GTWY agent is the fallback.
  3. Routing: let the agent pick the workflow (wf_start_workflow), or keep our router and start the agent already inside a workflow?
  4. Sync or webhook replies from GTWY? Webhook is more robust for long tool rounds; sync is simpler for the spike.
  5. Ask the GTWY team for: tool results in thread history, a per-call way to pass full history officially, and a human-approval interrupt. Each would remove a piece of our code later.
  6. Spike owner and the week-1 exit bar (pass^5 target, latency, cost).
