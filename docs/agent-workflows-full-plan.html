Agents run the canvas workflows

The complete plan to replace the DBOS runner loop with Mastra agents: one supervisor that talks to the customer and picks the workflow, and one agent per workflow that carries it from start to end. Our server keeps the state and checks every move.

Summary

The decision in 5 lines

  1. The DBOS runner loop and our one-off AI calls (route, checkTopic, decideStep, chooseCase, compose) are replaced by Mastra agents.
  2. A supervisor agent handles every customer message: it picks the workflow, notices topic changes and off-topic replies, and hands the turn to a workflow agent.
  3. Each workflow agent sees a read-only map of its canvas plus the current step, and moves forward only by calling wf_* tools.
  4. Our step engine (engine.ts) owns the state. It accepts or rejects every move with a reason. The model never writes state directly.
  5. Postgres state, the per-ticket event inbox, the timer sweeper, approvals and idempotency stay ours. The canvas does not change.

Ground rule for the whole doc: the server owns state. Agents propose moves; the engine decides whether they happen. Anything that reads "the agent does X" means "the agent asks for X through a tool, and the server checks it".

How it works today

Each workflow run is one DBOS workflow, runWorkflow in server/src/runner/workflow.ts, with the id run:<runId>. The loop checkpoints each step, so a crash resumes where it stopped.

  • decide / act / advance (runner/steps.ts): one block at a time. AI steps call decideStep; AI conditions call chooseCase; rule conditions run in code (chooseByRules).
  • facts (workflow_run.facts): collected values, tool outputs, chosen cases, attempts, loop visits, variables, the trail of finished items.
  • outbox: replies built during a turn. AI notes are merged by compose; text bubbles go out word for word.
  • recv: the run sleeps on a DBOS signal with a deadline (the reminder, then expiry: 120 s and 600 s by default in config.ts).
  • route (llm/decider.ts): picks a workflow for a new message. gate maps confidence to human (≥ 0.8 wants human), start (≥ 0.7), clarify (≥ 0.4) or a free reply.
  • topic check (run-control.ts → checkTopic): only while a run waits on the customer. new_request with confidence ≥ 0.8 cancels the run and starts the new workflow. neither marks the input as "not an answer", so it asks again.
  • Timeline: every step writes run_event rows through addEvent; the run panel reads them.

Limits

  • One block per AI call. The AI never sees the workflow ahead, so it can't use an answer the customer already gave for a later step.
  • Several separate AI calls per message (topic check, decide, choose case, compose) add latency and cost.
  • The control flow is hand-written. Every new block type or edge case means new runner code.
  • The topic check only runs while a run waits on the customer.
  • DBOS adds a second store and its own concepts (checkpoints, recv, signals) for what is mostly "wait for the next event".

Supervisor agent

  • Gets every customer message first. Sees the recent conversation, the list of published workflows (name and "when to use") and the active run, if any (workflow, current step, what it is waiting for).
  • Decides one of: continue the active workflow, start a workflow, switch to another workflow, the reply is not an answer, off-topic question, wants a human, or no workflow fits.
  • Replaces route(), gate() and checkTopic(). The same thresholds become rules in its prompt, and the server checks them again in wf_start and wf_switch_workflow.
  • Writes customer text only when no workflow handles the turn (clarifying question, free reply, handoff note).

Workflow agent (one per workflow)

  • Owns the conversation for its workflow from the first step to the end.
  • Gets a read-only workflow map, generated from the canvas on publish: steps, branches, what each input collects and its format, the tools each step may call, loop limits.
  • Gets the current step card and progress from the engine on every turn and in every tool result.
  • Can call only the wf_* tools and the actions the current step allows. The map lets it plan; the engine decides.

Server guards

  • engine.ts is a pure module: given the workflow, the facts and a requested move, it returns the new facts and the next step, or a rejection with a reason.
  • Rejected moves include a skipped step, a case that is not in the current condition, an input in the wrong format, a loop over its limit, an action outside its step, and an action that needs approval but has none.
  • A rejection is returned to the agent as a tool error it can act on, for example "Step 2 still needs order_id. Ask the customer for it."

Stays ours

  • Postgres state: workflow_run, facts, run_event, approval_task, action_run.
  • Event inbox: one row per trigger, processed one at a time per ticket.
  • Timer sweeper: reminders, expiry, approval timeouts and the resume window.
  • Approvals and idempotency: approval tasks, and one key per side effect.

In the POC a ticket is a row in conversation; "ticket" below means that row.

Hand-off between agents

We use delegation (agents as tools). The supervisor calls a workflow agent the way it calls a tool, and gets the result back in the same turn. Control always returns to the supervisor before the next customer message.

Handing over

  1. The supervisor decides "continue" or "start". For a start, it calls wf_start(workflow) and the engine creates the run.
  2. It calls the workflow agent with the workflow key and an intent: answer, not_an_answer, off_topic (with a one-line answer to include) or resume (after an approval or timer).
  3. The workflow agent runs its tool loop and writes the reply. That reply is what the customer sees.

Taking back control

  • On the next message the supervisor runs first again, so it sees every topic change, not only those during a wait.
  • The workflow agent can also call wf_yield(reason) when the customer clearly wants something its workflow cannot do. The supervisor then picks again in the same turn.
  • When the run ends (completed, escalated, expired), the next message goes to the supervisor with no active run.

Shared ticket memory

  • One Mastra memory thread per ticket (thread = ticket id, resource = customer). Both agents read the same conversation.
  • Workflow progress is not stored in agent memory. It comes from the engine each turn, so a new or restarted agent always sees the same truth.
  • The workflow agent gets the last 20 messages plus the engine's progress summary, not the whole thread.
Unverified: how Mastra passes memory to a delegated agent (shared thread or a copied context) must be checked in Stage 1. If it does not share cleanly, the dispatcher passes the recent messages explicitly.

One voice

  • A shared style guide is the first part of every agent's prompt: tone, length, language, no promises a tool has not confirmed, no internal terms.
  • Only one agent writes the customer reply per turn. The supervisor does not add text when it delegates; it passes any off-topic answer to the workflow agent to include.
  • Text bubbles are delivered by the workflow agent inside its reply, word for word. The server checks the reply before sending it (see Tool contract).

Tool contract

Every tool runs through engine.ts in one database transaction. The ticket id and run id come from the request context, never from model arguments. Every successful call returns the same shape:

{ ok: true, progress: "Step 2 of 5 done: order_id = ORD-5006",
  next: { step: "Check order", type: "ai_step", instruction: "...", tools: ["call_lookup_orders"] },
  say: ["We are checking your order…"] }           // bubble text the agent must include word for word
{ ok: false, reason: "order_id is missing", fix: "Ask the customer for the order ID (looks like ORD-5001)." }
ToolArgumentsServer checksReturns
wf_start (supervisor)workflow key (enum), confidence, reasonPublished and enabled; no active run; confidence ≥ 0.7First step card
wf_save_inputinput id, valueThe input is in the current step or one already reachable; format check (checkAnswer); attempts ≤ 3Next step card, or the format error
wf_choose_casecondition id, case id (enum), reasonCurrent step is an AI condition; case belongs to itFirst step card of the branch
wf_complete_stepstep id, summaryStep is current; required actions ran; save-response mappings appliedNext step card
call_actionaction key, args (strict schema)Allowed in the current step; schema valid; approval rule; idempotency key ticket:step:visitResult, or "waiting for team approval"
wf_wait_for_customerwhat is neededThe current step needs something from the customerOK; reminder and expiry timers set
wf_switch_workflow (supervisor)workflow key, confidence, reasonDifferent workflow; confidence ≥ 0.8Old run cancelled; first step card of the new one
wf_resume (supervisor)reasonRun expired inside its resume window; same workflowRun reopened at the same step, answers kept
wf_yield (workflow agent)reasonAn active run existsOK; supervisor decides next
wf_handoffreasonNoneRun escalated; bot stays quiet on the ticket
  • Forward answers. wf_save_input accepts an input that appears later in the map, if the path to it does not depend on an unresolved condition. That lets the agent use "my order ORD-5006 never arrived" for two steps at once, without skipping anything.
  • Rules run inside tools. When a move lands on a rule condition, a text bubble or a loop edge, the engine resolves it in the same call and reports it in say and progress.
  • Bubble check. Bubble text from say is held as pending on the run. Before the reply is sent, the server checks that it contains each pending bubble exactly. If not, the agent is asked once to rewrite it; if it fails again, the server adds the missing bubble text to the reply. A bubble is marked delivered only when the reply goes out.
  • Step-scoped tools. Each turn the agent is given only the wf_* tools plus the actions of the current step.
  • Hard rejection log. Every rejected call writes a move_rejected event, so we can count invalid-move attempts.

One customer message, end to end

Example: the customer is in "Item return", waiting at input 1.1 (order id).

sequenceDiagram
  participant Cu as Customer
  participant In as Inbox + dispatcher
  participant Sv as Supervisor
  participant Wa as Return agent
  participant En as Engine
  participant Te as Team
  Cu->>In: "ORD-5006, the jacket is too small"
  In->>Sv: event (ticket locked)
  Sv-->>Sv: continue, intent = answer
  Sv->>Wa: delegate(item_return, answer)
  Wa->>En: wf_save_input(order_id, ORD-5006)
  En-->>Wa: ok, next 1.2 lookup
  Wa->>En: call_action(lookup_orders)
  En-->>Wa: Delivered → rules → step 2.1
  Wa->>En: wf_save_input(reason, "too small")
  En-->>Wa: ok, next 2.2 create return
  Wa->>En: call_action(create_return)
  En-->>Wa: waiting for team approval
  Wa-->>In: "Thanks! I've asked the team to approve your return."
  In->>Cu: reply, lock released
  Te->>In: approved (event)
  In->>Sv: event approval_decided
  Sv->>Wa: delegate(item_return, resume)
  Note over En: engine already ran create_return
bubble 2.3 comes back in say
  Wa-->>Cu: "Good news, the team approved it. Your return is booked…"
  1. The message is saved and an inbox event is added. The dispatcher takes the next event for this ticket and locks it.
  2. The supervisor reads the active run (waiting at 1.1) and the message, and decides continue.
  3. The return agent saves the order id, runs the lookup, lands on step 2 through the rule condition, and saves the reason from the same message.
  4. The create-return action needs approval, so the engine creates an approval task and sets the run to waiting_approval. The agent tells the customer.
  5. When the team approves, an approval_decided event comes in. The engine runs the action first, then the agent is called with resume to tell the customer.
  6. If the customer had sent no order id, the agent would call wf_wait_for_customer and ask. The run waits with reminder and expiry timers.

What GTWY has today (checked in the gtwy-ai source)

The only OpenAI-style route is POST /api/v2/model/openai/responses. It is a wrapper around a GTWY agent, not a pass-through:

  • It requires an agent_id, and that agent's prompt and settings apply.
  • It merges the input into one user text; roles are lost, and the messages field is not used.
  • It drops tools and returns text only, so no tool calls come back to Mastra.
  • No streaming. Usage is returned; cost is logged inside GTWY.
  • There is no /v1/chat/completions route that callers can use.

Mastra's agent loop needs the full message list and tool definitions, and tool calls returned without running them. So the hybrid needs a new GTWY endpoint: /v1/chat/completions pass-through that takes messages, tools and tool_choice, returns tool_calls unexecuted, and keeps GTWY's key handling, cost logging and spending limits.

Recommendation: use the hybrid if the GTWY team can provide that endpoint. Until then, start with pure Mastra and a direct key, with the provider and model in config, so moving to GTWY later is a config change.

Cost tracking

  • Token usage: Mastra returns usage per model call and records it in its traces. We copy it into our own table after every call.
  • Dollar cost, two options:
    • Langfuse through Mastra's exporter. It prices tokens per model. Cloud has a free tier with a monthly event limit; self-hosting is open source and free apart from hosting. verify current limits and price
    • Our own table: llm_usage (ticket_id, run_id, agent, model, input_tokens, output_tokens, cached_tokens, cost_usd, created_at), priced from a small model_price table we maintain.
  • Recommended: our own table from Stage 1, because spending limits and the run panel need it anyway. Add Langfuse for traces if it is allowed.
  • Spending limits: the dispatcher checks the cost per ticket and per org per day before each turn. Over the limit → handoff with "AI budget reached". With the hybrid, GTWY's limits also apply.

Reliability and quality

Reliability

  1. One turn per ticket at a time: the inbox lock.
  2. Retries: a failed model call is retried twice with backoff, then the event is retried later. After 3 failed attempts the ticket is handed off with "AI unavailable".
  3. Idempotency: every action uses the key ticket:step:visit; a repeat returns the stored result from action_run. Inbox events have unique ids, so a duplicate webhook is dropped.
  4. Crash recovery: the event is marked done only after the reply is saved. A crash mid-turn re-runs the turn; engine state is already committed per tool call, and idempotency stops repeated side effects. Replies are saved before sending and deduplicated by turn id.
  5. Iteration limits: at most 8 tool calls per turn and 30 turns per run. The same step rejected 3 times in a row → handoff.
  6. Version pinning: a run keeps the workflow version and map it started with.

Quality

  • Scripted chats: about 20 per workflow, covering the happy path, early answers, wrong formats, "I don't know", topic switch, off-topic questions, approval rejected and silence.
  • pass^5: each chat runs 5 times; a chat passes only if all 5 pass. Checks read the database (final state, steps visited, actions run), not only the text.
  • Invalid moves: count the move_rejected events per chat. Accepted invalid moves must be zero, because the engine should reject them all.
  • Tone: a judge model scores replies against the style guide.
  • Tracing: each turn stores the supervisor decision, tool calls, rejections, tokens and cost as run_event rows; Mastra traces (and Langfuse, if used) hold the full model calls.
  • The test suite runs on every prompt, map-compiler or model change.

Stages

Stage 0
2–3 days

Decide model access and storage

  • Ask the GTWY team for the pass-through endpoint described in Model access; agree a direct provider and key for now.
  • Mastra storage in our Postgres (a separate schema); cost table; Langfuse yes or no.
  • Exit: provider, model and storage agreed and written down.
Stage 1
1–1.5 weeks

Engine, Mastra, tools

  • Extract engine.ts from steps.ts: next step, inputs, conditions, loops, approvals, save response. No DB, DBOS or AI inside.
  • The current runner calls the engine, so nothing changes for users. Unit tests for each block type.
  • Add Mastra with Postgres storage. Build the wf_* tools on the engine; tables ticket_event, ticket_timer, llm_usage; dispatcher and sweeper.
  • Map compiler: canvas → agent_map on publish.
  • Exit: runner behaviour unchanged (tests and one real chat); every tool tested through a dev endpoint, including each rejection.
Stage 2
1 week

One workflow agent (spike)

  • One workflow agent, no supervisor yet: our router starts the run, then the agent handles "Item return" end to end, with the map, approvals and timers.
  • Per-run switch workflow_run.engine = 'runner' | 'agent'.
  • Run the scripted chats twice, with and without the map. Measure invalid-move attempts, tokens per turn and pass rate.
  • Exit: ≥ 95% pass^5; zero accepted invalid moves; under about 6 s per reply; known cost per ticket.
Stage 3
1.5–2 weeks

Supervisor plus agents per workflow

  • Supervisor with wf_start, wf_switch_workflow, wf_handoff and delegation. route() and checkTopic() are no longer called for agent runs.
  • One workflow agent per published workflow, built from the shared base plus its map.
  • Resume window for late replies; spending limits.
  • Rollout: playground, then a share of real tickets, with the runner as fallback. Remove the DBOS runner after two stable weeks.
  • Exit: the Stage 2 bar holds with the supervisor; topic-switch and off-topic chats pass; latency still under about 6 s.

Total: about 4–5 weeks for one engineer, with a go/no-go at the end of Stage 2.
